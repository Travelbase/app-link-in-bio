# Architecture rules
- Link-in-bio content lives in `pages` + `blocks` (jsonb content per block type); code never hard-codes page content — so teams edit without deploys.
- `PageRenderer` renders plain page+blocks data and all block components read design via `useTheme()` — so the editor preview can reuse it with unsaved data.
- UTM tagging goes through `withUtm` in `src/lib/linkinbio/utm.ts` (source pattern in `utmSourceFor`) — one place to change tracking.
- Access rules are prototype-open and named "Prototype open ..." — tighten when sign-in arrives.
- Fixed UI strings live in `src/lib/uiText.ts` until a translation system exists.
- Creator home (`/`) starts without a selected page, so opening the creator never silently picks a team's page. `/edit/:address` keeps a working copy in `useEditorState` and autosaves the whole page + block list ~1s after changes to the draft (`pages.draft`, jsonb `{ page, blocks }`). The `pages` + `blocks` rows are the published version: visitors only ever read those, and "Publish" copies the draft into them and clears it. Public reads (`server/api/public.ts`, `publicPage` in `supabase.ts`) never return the draft.
- Instagram grid posts, the bit.ly link and new pages go live at once; only page settings and blocks wait for Publish. The daily avatar refresh writes both the live Profile block and an open draft.
- Undo/redo is browser memory in `useEditorState` (`src/lib/linkinbio/history.ts`), lost on reload; edits of one kind within 1s are one step. Cmd+Z, Shift+Cmd+Z and Ctrl+Y work everywhere in the editor.
- Addresses "edit", "admin", "api", "settings" are reserved (DB check + `RESERVED_ADDRESSES`) — so editor routes never clash with pages.
- Editor uses zinc/teal via `html.editor-theme` CSS variables — internal-tool look without touching public pages.
- Image uploads go by XHR (for progress), max 5 MB (photos are scaled in the browser first): straight to the `page-images` bucket on Lovable Cloud, through `/api/images` to the Cloud Storage bucket `travelbase-link-in-bio-images` in production.
- Every image field opens `ImagePickerDialog`, Amigo's sources: Media Search, Google Drive and Unsplash go through Core's `_actions` from `server/lib/picker.ts` (Core token with `use:media-picker`), never from the browser; a pick is uploaded like a file, so it lands in the same bucket. Staging offers the computer only.
- Optional CTA accent belongs to page design; the Travelbase footer logo is a per-page `show_travelbase_logo` toggle (URL constant in presets.ts), with an optional custom `footer_logo_url` overriding it; branded card treatments are activated by the Travelbase house-style design so other pages retain their look.
- Instagram tokens and one-time OAuth requests stay in server-only tables; public post rows expose only copied media, captions and editable links — never put Meta credentials in browser code.
- Instagram sync lives on the server (edge functions on Lovable Cloud, `server/lib/instagram.ts` in production) and stores images in the image bucket; manual grid content remains separate so disconnect can fall back without rewriting blocks.
- The daily Instagram sync is pg_cron + `internal_job_secrets` on Lovable Cloud, and the Cloud Run Job `link-in-bio-daily` (Cloud Scheduler, 05:00 UTC) in production.
- Standard template has one row per language (`standard` = NL/BE, `standard-fr`, `standard-de`, `standard-uk`), picked by the page's `market` — texts stay in the database, not code.
- Instagram login before a page exists is parked in server-only `instagram_pending_connections` under a one-time hashed key, claimed after the page is created — so tokens never reach the browser.
- Incomplete blocks (missing required link/image, see `isBlockComplete`) are hidden publicly and dimmed in the editor preview — nothing half-finished goes live.
- The daily sync refreshes the Profile avatar from Instagram unless `avatar_custom` is set on the profile block (set when the team uploads a photo).
- Analytics: page visits come from Bitly (each page gets a bit.ly link in production, `page_short_links`), clicks per button from GA4 through the UTM tags. No home-made tracking — no cookie banner and nothing to store.
- Two environments, two branches: Lovable syncs to `lovable` (staging on Lovable Cloud, test data, no Instagram); a developer merges `lovable` into `main`, which deploys to GCP (Cloud Run + Cloud SQL, Instagram and Bitly). Environment-specific URLs come from env/config, never hard-coded.
- All data access goes through `LinkInBioBackend` (`src/lib/linkinbio/backend/`): `supabase.ts` for Lovable, `http.ts` for production, picked by `VITE_DATA_BACKEND`. New data access is a method on that interface, in both implementations; components never import the Supabase client — so Lovable work still runs in production after the merge.
- Migrations are additive only (add tables and columns, never drop or rename). Whoever merges `lovable` into `main` ports new `supabase/migrations` to `server/migrations` and new edge-function logic to `server/`.
- Production lives under `/a/link-in-bio/` behind the apps gateway (staff login); public pages, their assets and Meta's callbacks sit under `/a/link-in-bio/public/`, the only prefix without login. Paths go through `src/lib/linkinbio/urls.ts`.
- Brand colours come from Amigo (Core API, `server/lib/amigo.ts`), never a copy in this app; a page keeps only the brand code it is linked to (`pages.brand_code`, production only).
